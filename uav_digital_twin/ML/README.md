# ML — engine anomaly detection

Two detectors live side by side:

| | Files | Backend uses it |
|---|---|---|
| **v1** | `fault_detector.py`, `train_model.py`, `models/isolation_forest.pkl` | no (kept for comparison) |
| **v2** | `fault_detector_v2.py`, `engine_features.py`, `train_model_v2.py`, `models/engine_model_v2.pkl` | **yes** (see [Switching](#switching-the-backend-to-v2)) |

Both return the same result shape, and both use the fault rules in `fault_detector.py` to *name* the
fault (OVERHEATING, MISFIRE, ...). They differ in how they decide a reading is abnormal.

## Workflow

Run from `uav_digital_twin/`:

```bash
python ML/generate_dataset.py     # ~10 s  -> ML/data/*.csv  (add --quick for 10% size)
python ML/train_model_v2.py       # ~20 s  -> ML/models/engine_model_v2.pkl
python ML/evaluate_models.py      # ~1 min -> compares rules vs v1 vs v2
```

`ML/data/` is git-ignored. Every simulated flight has a fixed seed, so the same command rebuilds the
same files on any machine.

## Datasets

All generated by `sensor_simulator.py` at 1 reading per second. Every row carries ground-truth columns
(`phase`, `true_fault`, `fault_stage`, `fault_severity`); training never looks at them.

| File | Contents | Used for |
|---|---|---|
| `train_normal.csv` | 32 h healthy, full mission (takeoff, climb, cruise, loiter, descent) | learning what normal looks like |
| `val_normal.csv` | 20 h healthy, different seeds | setting the alert thresholds |
| `test_normal.csv` | 28 h healthy: mission, steady cruise, and mission with 2× sensor noise | measuring false alarms |
| `test_faults.csv` | 36 h with 204 fault episodes (all 8 types), mission and cruise | measuring detection |

To change sizes, noise levels or profiles, edit `DATASETS` in `generate_dataset.py`.

## How v2 works

v1 feeds raw sensor values to an Isolation Forest trained on one steady cruise point. That makes every
other flight phase look abnormal, misses faults that show in only one sensor, and can't see slow drift.
v2 changes the inputs:

1. **Expected value.** For each sensor, a gradient-boosting regressor learns the healthy value from RPM
   and RPM's 10 / 60 / 300 s averages (the averages account for CHT and oil temperature heating up
   slowly). The **residual** is `(reading − expected) / healthy spread`, so "CHT is too hot *for this
   RPM*" stands out, while a normal hot climb doesn't.
2. **30 s rolling mean** of each residual. Averaging removes most noise, so small drifts show early.
3. **Two detectors** on those 9 features:
   - **Isolation Forest**: an unusual *combination* of sensors.
   - **Residual limit**: any *single* sensor too far from expected. An Isolation Forest can't do this
     job; in tests, one sensor 100 standard deviations off scored the same as a healthy reading.
4. **Thresholds** are set on the validation data so a healthy engine produces at most ~0.5 flagged
   readings per hour (`--false-flags-per-hour`).

An RPM-jitter feature was tried and dropped: it mostly measured RPM sensor noise, and with 2× noise it
flagged 58% of healthy readings.

`evaluate_models.py` also checks that the live detector (one reading at a time) produces exactly the same
scores as the batch evaluation, so training and live use can't drift apart.

## Results

From `evaluate_models.py` on the datasets above.

**False alarms on a healthy engine** (dashboard alerts per hour, with the share of readings flagged in brackets):

| | rules only | v1 | v2 |
|---|---|---|---|
| Steady cruise | 0 | 0 (0%) | 0.2 (0.0%) |
| Full mission | 0 | 2.7 (**59%**) | 0.2 (0.1%) |
| Full mission, 2× sensor noise | 0 | 2.5 (59%) | **11** (2.6%) |

v1's alerts-per-hour looks low only because it flags non-cruise phases continuously, which merges into a
few very long alerts.

**Fault episodes** (median over 204 episodes):

| | Episodes found | Fault severity at first alert | Seconds into the fault |
|---|---|---|---|
| rules only | 99% | 63% | ~150 s |
| v1 (cruise runs) | 99% | 48% | 122 s |
| v2 | **100%** | **8%** | **34 s** |

v2 alerts about **110 s before the rules** for every fault type, including single-sensor faults (abnormal
vibration, sensor drift) that v1 can't see. The alert is `UNKNOWN_ANOMALY` until a rule names the fault;
the rules name it correctly in 99% of episodes.

## Limitations

- **Simulator data only.** v2 learned the simulator's engine behaviour, which is invented (RPM explains
  98% of CHT here). A real engine is messier, so these numbers show that the method works, not how
  accurate it will be. Retrain and re-check on real engine logs before relying on it.
- **Sensitive to noise level.** Thresholds match the noise in the training data. With 2× noise, v2 raises
  ~11 false alerts per hour. Set thresholds using data from the actual sensors, or generate training data
  at the matching `noise_scale`.
- **RPM is the only context.** Airspeed, altitude and outside air temperature aren't sensors here, so their
  effects show up as residual.
- **Time-based.** v2's windows use reading timestamps, so `sensor_simulator.py --speed 5` makes it
  detect later (in readings) than at normal speed.
- **Per-engine memory.** v2 keeps the last 30 s per `engine_id` in memory. A backend restart clears it,
  and the first seconds after that are slightly less sensitive.
- **Different score scale.** v2's `anomaly_score` is below 0 when anomalous, like v1's, but the
  magnitudes are much larger (−20 to −27 for a clear fault in the live run). The
  `fault_events.confidence` column (`abs(anomaly_score)`) changes scale with it.

## Switching between v1 and v2

`main.py` currently imports v2:

```python
from ML.fault_detector_v2 import detect_fault   # v2 (current)
# from ML.fault_detector import detect_fault    # v1
```

The result keeps v1's keys and adds `flagged_by` (`rules`, `isolation_forest`, `residual_limit`). The
dashboard works with either.
